# 阶段 22 执行日志（阶段 D v2：换工作负载 + 评分制 cover）

## 本单元做了什么

phase21 的结论是"工作负载选错了"：`targets_hard` 恰好是 Solver 最不擅长的那些，
留不出可测量的余量。本单元按那份结论改造测量：

| 改动 | 说明 |
|---|---|
| `--select {hard,nearmiss,easy,mixed}` | 按**难度**选工作负载：难度取自修正后的 G1 报告里的逐目标 `solve_rate`。默认 `nearmiss`（`0 < rate < 1`）——那是 `cover` 唯一有信号的地方 |
| **评分制 cover** | `cover(S) = Σ_w [ rate_with(S,w) − rate_without(S,w) ]`，`rate = 通过数 / k`（没生成出证明也算失败，分母固定） |
| 新增判定码 `negative` | 给库后反而更差时单列，不允许混进 `no_gain` |
| **预检** | 实验前先用一条最便宜的作业验证处理臂的 import 真的可用 |
| `library_citations` 指标 | 统计处理臂里**真的引用了 `sgs_lem_*`** 的证明数——见下面的"关键诊断" |

## 踩到的坑（差点得出一个假结论）

第一次跑 D v2 的结果是：

```
评分制 cover：基线 3.75 → 给库 0.0（增益 -3.75）
二值口径：proved_cover(∅)=5  proved_cover(S)=0
```

**"给库之后所有目标都证不出来了"**——这个数不可能是真的。查下去发现处理臂的**判定全是空字符串**，
子进程日志写着：

```
error: object file '...\.lake\build\lib\lean\SgsLean\GeneratedLibrary.olean' ... does not exist
```

**根因**：`lake build SgsLean`（**库目标**）不会把 `SgsLean.GeneratedLibrary` 编进去——
它报 `Build completed successfully (208 jobs)`，但 olean 根本没生成。
必须用**模块目标**：`lake build SgsLean.GeneratedLibrary`（那一次顺带重编了 3 个 Mathlib 模块，
正是 phase6 记过的"本地补编"那三个）。

修完之后处理臂的环境才真的能 `import SgsLean.GeneratedLibrary`，
而这条正是"库可用"的**必要条件**——否则处理臂只是"提示词里多了一段文字"。
为防止同类问题再次伪装成结果，harness 里加了**预检**：环境不可用就直接退出，不让数据流进报告。

**净增益为 0**：有一条因库而多证出，也有一条反而掉了——在 k=4、6 条目标上这属于噪声。

## 两个必须记住的观察

**观察 1：处理臂生成的证明明显更少（17 vs 24）。** 提示词里多一个库区块会改变模型的输出分布
（一条目标从 4 篇掉到 0 篇）。所以 `rate` 的分母固定用 `k` 而不是"实际生成数"——
否则"少生成几篇"会虚高成绩。这个副作用在后续 H2 里必须控制（同预算、多次采样）。

**观察 2（关键诊断，已加进 harness）：处理臂里有多少证明真的引用了 `sgs_lem_*`？**
如果几乎没人引用，那么这一臂实际是"提示词多了一段文字"，增益为 0 就**不能**归因于"库没用"。
这个数在下一轮跑出来之前，`no_gain` 的解读要保留。

## 现状与下一步

**阶段 D 的测量装置现在是可信的**（真 cover、评分制、环境预检、引用计数），
但当前规模（库 4 条、目标 6 条、k=4）没有足够功效测出增益。

下一轮要做的三件事（按性价比排序）：

1. **先扩库**：跑阶段 B+C 的完整流水线，把库从 4 条扩到 15–30 条
   （库现在只覆盖 2–3 个目标，一条引理帮不上它没涉及的目标）；
2. **提高功效**：`--select mixed`（近失手 + 稳定可解）+ `k=6~8` + 重复 2–3 次，
   看增益的置信区间，而不是单点数字；
3. **看引用率**：若引用率接近 0，说明问题在"提示词没让模型用库"，而不是"库没用"——
   那是可以先解决的问题（把库引理的适用场景写得更具体，或改用"先检索再证明"的两段式）。
