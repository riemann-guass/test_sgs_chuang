# 数据划分与实验协议（先定这个，再跑实验）

> 起因：phase19–22 里，我把 **miniF2F 的目标**同时当成了"建库的输入"和"评测的对象"。
> 那样得到的增益是**自我循环**的，不能作为任何结论。这份文件把"哪块数据用于什么"钉死，
> 之后所有实验都必须按它执行。

## 一、三块数据，职责严格分开

| 数据集 | 角色 | 谁可以读它 | 绝对禁止 |
|---|---|---|---|
| **C 课程集（Curriculum）** | 建库：需求挖掘 → 猜想 → 硬门 → 求解 → 入库 | 生成层、判据层、选择层——**全部** | — |
| **D 开发集（miniF2F valid）** | 调参：选工作负载、定 k、采样量、debug、看方向 | 测量与消融 | 进库；进需求挖掘；作为生成候选的来源 |
| **T 测试集（miniF2F test）** | 最终评测 | **只在框架冻结后跑一次** | 任何调参、任何建库、任何需求、任何"看看效果" |

## 二、四条不可违反的规则

1. **库里绝不允许出现来自 D 或 T 的引理**——包括"由它们的子目标生成的候选"。
   判断标准是**来源**，不是文本相似度：只要某条候选是为 D/T 的某个目标而生成的，它就不许进库。
2. **需求挖掘只能在 C 上做**。需求是"库的缺口"，用 D/T 挖需求等于把测试集的信息带进库。
3. **D 可以反复用**（调参、修 bug、看趋势），但论文/报告里必须写明：所有超参与工作负载选择都在 D 上完成。
4. **T 只跑一次**，且在"框架 + 超参 + 评测脚本"全部冻结之后；结果无论好坏都如实报告。

## 三、C（课程集）从哪来——三个候选来源

| 来源 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| **C1 自建初等引理集** | 已有的 `data/lemmas_g1.jsonl`（63 条）+ `data/workload.jsonl` | 完全与 miniF2F 无关；已验证可跑 | 与 Mathlib 级难度有差距 |
| **C2 Mathlib 定理** | 从 Mathlib 里取定理（如 MathlibLemma 那类 folklore 引理） | 难度贴近目标域 | 需要挑题规则，工作量大 |
| **C3 SGS 的 D_3k** | `D:\bianma\code\SGS\data\D_3k_prover_dataset.json`（~3000 条 Lean4 题） | 现成、规模大、与 miniF2F 不同源 | 需要 Lean 4.15 环境，与我们 4.28 不兼容，需转换 |

**建议先用 C1 把闭环跑通**（它是我们自己的、已验证可跑的），再考虑 C2/C3 扩大规模。

## 四、标准实验流程（按数据角色重写）

```
① 建库（只碰 C）
   多轮：C 上跑 Solver → 采轨迹 → 挖需求 → 猜想 → 硬门 → 求解 → 验证 → 入库
   → 得到库 L

② 开发（碰 C 与 D，绝不碰 T）
   · 在 D 上选工作负载分档（hard / nearmiss / easy）、定 k 与重复次数
   · 在 D 上先看"有库 vs 无库"的方向，确认装置没问题
   · 所有选择写进报告

③ 测试（只碰 T，跑一次）
   冻结 L、超参、脚本 → 在 T 上跑 baseline（无库）与 treatment（有库）
   → 报 pass@k 与差额、置信区间、成本

④ 审计
   在 C 上做形式化分量 vs 配对 Δ 的相关性（同样不许碰 T）
```

## 五、已经跑过的实验该怎么算

| 已跑的实验 | 用到的数据 | 定位 |
|---|---|---|
| G1（初等引理集） | C1 类数据 | 只验证 Solver 能力与装置，不是结论 |
| G1（miniF2F **valid**） | D | **开发测量**：说明装置与预算问题，不是最终结论 |
| 阶段 B 猜想（5 条 valid hard 目标） | **D** | **开发**：验证"猜想器接线"这件事，但它建的候选**不能进最终库** |
| 阶段 C 漏斗（4 条引理） | **D** | 同上——这批引理是**开发期产物**，最终库里必须换掉 |
| 阶段 D 两臂 cover | D（hard / nearmiss） | **开发**：验证测量装置；增益 0 不能作为结论 |

**一句话**：到目前为止，miniF2F 上的一切都是**开发结果**，它们的作用是"把装置修对"。
真正的结论要在 **C 上建库 → T 上只跑一次** 之后才有。

## 六、这条规矩会怎么改变下一步

原本要做的"拿 miniF2F 的 hard 目标扩库"——**取消**。改成：

1. 在 **C1（自建初等引理集 + 它派生的题）** 上跑多轮闭环，把库建起来（可以任意多轮，不污染 D/T）；
2. 用 **D（miniF2F valid）** 调工作负载与 k，确认装置正常；
3. 冻结之后在 **T（miniF2F test）** 上跑一次，出最终数字。

这也顺带解决了 phase19 遗留的"需求数据与目标集不匹配"问题：需求本来就应该在 **C** 上挖，
而 C 的题我们已经有了。
