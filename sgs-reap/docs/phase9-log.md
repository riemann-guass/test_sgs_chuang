## 分桶规则（跑之前定死）

| 跨 ≥ `min_targets` 个目标 | 有成功轨迹证据 | bucket | 含义 |
|---|---|---|---|
| 是 | 是 | `demand` | 真需求：够广且被成功证明支持 → N1 的输入 |
| 是 | 否 | `suspect_failure_only` | 出现很广但从没出现在成功轨迹里 → 可疑（共同的死路） |
| 否 | 是 | `local` | 局部需求：有成功证据但不够广 |
| 否 | 否 | `artifact` | 只在不成功轨迹里、且只在一个目标上 → 死路伪影的代理判据 |

判定：`demand` 条目 **≥ 3 条** → G2 通过（N1 成立）；否则 N1 降级，主线只留 N2 + N3。

### 闸门 G2：**通过**（5 ≥ 3），但附带两条必须写清楚的限制

**好的部分**：`n ≤ n * n + 1` 拿到最高分（freq=3、跨 2 个目标）——它既是目标 `g20` 的**目标本身**，
又是 `g38`（合取）证明过程里的**子目标**。这正是 N1 假设的形态：**同一条中间事实在多个目标上被需要，
而库里没有对应的可复用引理**。这条信号不是人造的，是两条真实参考证明撞出来的。

**限制 1：`P` 这种签名太粗。** 它来自 prop 级目标的裸假设名，跨目标重复只是因为不同引理都用了同一个变量名。
签名 v1 只用**主目标类型**，不含局部上下文 → 粗签名会污染需求榜。
**修法（P3 之前必须做）**：签名改为"上下文 + 目标"（例如 `P Q : Prop, h : P ∧ Q ⊢ Q`），
或至少要求签名包含 ≥1 个谓词符号才会被计入需求。

**限制 2：伪影这一支在整篇生成流水线下没被真正检验。** 干跑的 38 条全是参考证明（全成功），
`artifact` 桶是空的；这不是过滤器的错，而是**当前流水线没有"中间死路"**——整篇生成里失败表现为
"整篇不过"，中间步骤照样是正常子目标。死路伪影是 **MCTS 搜索**的产物，要等 P4 把 MCTS 轨迹接进来
才谈得上真正检验。为了让这条逻辑不是"写了没试过"，用零成本的 `--self-test` 把它钉住：

```
[g2-self-test] 分桶={'X': 'demand', 'A': 'local', 'B': 'local', 'C': 'artifact', 'Z': 'artifact'}
[g2-self-test] PASS（demand / artifact / local 三分支都被覆盖）
```

顺带一个**自测抓到的真实错误**：我第一版把期望写成 `C: local`，而按定义"只出现在失败轨迹里"的单目标签名
就该判 `artifact`——测试当场报 FAIL，说明这套断言不是空转（改的是期望，不是实现）。
