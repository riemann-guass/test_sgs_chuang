# LeanReuse 设计说明

本文是项目当前的权威设计说明。阶段日志和旧报告只用于追溯，不覆盖本文。

## 1. 目标

LeanReuse 接收一条完整的 Lean 4 命题，返回零篇或多篇通过 Lean 内核验证的证明脚本。
系统可以调用语言模型生成候选，但语言模型没有裁决权；只有 Lean 验证成功的候选可以输出。

项目希望回答一个具体问题：在不训练模型的前提下，维护一套经过验证且具有跨题使用证据的
小型引理库，能否以合理成本提高新题的证明成功率？

## 2. 两个阶段

### 在线证明

```text
读取命题
→ 检查命题能否被 Lean 正确解析
→ 从冻结库中检索相关引理
→ 生成若干候选证明
→ 批量交给 Lean 验证
→ 只返回验证通过的证明
```

在线证明是只读过程。一次求解产生的临时内容不会进入全局引理库。

### 离线建库

```text
在建库集上收集失败轨迹
→ 找出反复出现的证明需求
→ 生成候选引理并证明
→ 过滤平凡、重复或无法验证的候选
→ 在独立题目上试用
→ 发布有跨题使用证据的引理
→ 生成、编译并冻结新库
```

离线过程可以运行多轮。每一轮读取上一轮冻结库，最终发布下一版冻结库。

## 3. 为什么必须分开建库和测量

一条为某道题专门生成的引理，往往很容易重新帮助这道来源题。如果把这种引用算作复用，
系统会把“为原题量身定做”误判成“可以帮助其他题”。因此 miniF2F valid 被拆成：

- 建库集（`C-build`）：只负责发现需求和产生候选；
- 复用测量集（`C-measure`）：只负责给候选提供独立试用机会；
- 开发集（`D`）：只用于调参与排错。

miniF2F test 是最终测试集（`T`），在全部设计和参数冻结后只运行一次。

## 4. 引理的生命周期

候选引理通过四类检查后进入“待观察”状态：

1. 合式：Lean 能把文本解析为命题；
2. 非平凡：不能被固定的简单策略直接闭合；
3. 新颖：不是已有库条目的重复表达；
4. 可证明：候选本身有通过内核验证的证明。

之后系统在复用测量集上公平展示这些候选。只有满足最小展示次数，并被多个不同题目的通过
证明实际引用，候选才变成“已发布”。试用充分仍无证据的候选变成“已停用”。

代码字段分别是 `probation`、`active` 和 `cold`。在线证明只读取 `active`。

## 5. 什么叫实际使用

对于引理 `l`：

```text
reuse(l) = 实际引用 l 的不同测量题数量
cost(l)  = l 放入模型提示词时的 token 数
score(l) = reuse(l) / cost(l)
```

实际引用必须同时满足：

- 整篇证明已经通过 Lean 验证；
- 引用来自 Lean 证明项的常量集合；
- 当前题不是该引理的来源题；
- 同一题引用多次仍只计一次；
- 该引理确实在本题提示词中出现过。

这个数量只说明引理被使用过，不证明它造成了成功。因果效果由有库/无库配对比较测量。

## 6. 检索与提示词

检索先按当前命题的符号和结构找相关引理，再在相关结果中结合跨题使用次数与 token 成本排序，
最后按提示词预算截断。不能先按全库使用次数排序，否则少数高频但无关的引理会长期占据提示词。

测量模式只中性说明哪些引理可用，避免诱导模型刻意引用。面向用户的产品模式可以主动建议
检查相关引理，但这种引用不回写正式复用记录。

## 7. 正确性边界

- 命题必须是闭式的，或者自行用 `∀`、`→` 等绑定全部局部变量。
- `sorry`、`admit`、未关闭目标、未知常量和超时证明都判失败。
- 模型服务只生成文本，不决定证明是否正确。
- 生成库必须先物化、编译并通过 import 预检，才能用于在线证明。
- 报告必须区分模型失败、输入拒绝和服务故障。

## 8. 评测

主指标是目标级 `pass@1` 和 `pass@k`：每道题生成 `k` 篇证明，只要至少一篇通过验证，
这道题就算成功。正式方法结果只统计首轮模型生成，不混入自动修补或廉价 tactic。

除正确率外还报告：token、每道成功题的成本、失败类型、库规模、引理使用分布，以及同一题
有库与无库的配对差值。

## 9. SGS 的位置

项目最初受 SGS 的“求解、提出辅助命题、筛选”分工启发，但不是 SGS 训练复现。SGS 通过
训练更新求解器；LeanReuse 冻结模型参数，只允许经过验证的引理库连接离线工作和在线求解。
SGS Guide 仅保留为后续实验的一个对照方法，不属于产品名称或核心正确性假设。
